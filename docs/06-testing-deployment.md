# 06. 검증, Vercel 배포, 완료 기준

검증은 **예상한 동작이 실제로 나오는지 확인하는 작업**이다. 이 문서에서는 코드 자체 검사, 실제 외부 연동 검사, 배포 검사를 구분한다. 문서를 읽었거나 코드를 작성한 것만으로 통과 처리하지 않는다.

## 1. 검사 단계와 도구

| 단계 | 도구·방법 | 실제 API 키 |
| --- | --- | --- |
| 단위 검사 | Node `node:test`, `assert/strict` | 불필요 |
| API 계약 검사 | 주입된 가짜 OpenAI·DB 어댑터와 표준 Request/Response | 불필요 |
| 브라우저 검사 | Playwright Chromium, 네트워크 응답 가로채기 | 불필요 |
| 실제 연동 검사 | 개발 서버 + 실제 OpenAI + 개발용 Supabase | 필요 |
| 배포 검사 | Vercel Preview 후 Production | 필요 |

테스트용 응답과 장애 주입은 테스트 코드에만 둔다. 운영 API에 `?mock=true`, 실패 강제 쿼리, 임의 모델 선택 옵션을 만들지 않는다. 어댑터를 바꿔 끼우는 방식으로 API 호출 횟수와 저장 데이터를 확인한다.

```sh
npm ci
npm test
npx playwright install chromium
npm run test:e2e
```

`playwright.config.js`에서 baseURL을 `http://localhost:3000`으로, webServer.command를 `npm run dev`로 설정한다. 개발 중 재사용은 허용하되 CI에서는 기존 서버를 재사용하지 않는다. 단위 검사는 `tests/unit/`, E2E는 `tests/e2e/`만 탐색하게 한다.

## 4. 화면·접근성 검수

02 문서의 디자인 토큰을 적용한 뒤 360×800, 768×1024, 1440×900에서 각각 확인한다.

- [ ] idle, loading, positive, negative, neutral, error를 실제 브라우저에서 열어 캡처한다.
- [ ] 767px/768px 경계에서 1열/2열 전환이 명확하고 가로 스크롤이 없다.
- [ ] 2,000자 입력과 200자 이유가 카드 밖으로 넘치거나 잘리지 않는다.
- [ ] 200% 확대와 키보드 전용 조작에서도 주요 기능이 가능하다.
- [ ] 파스텔 배경에서 일반 텍스트 대비 4.5:1 이상, 큰 글씨·주요 UI 경계는 해당 기준을 만족한다.
- [ ] 감성은 색상뿐 아니라 글자로 구분하고 초점 표시가 보인다.
- [ ] loading 알림·오류 알림·결과 알림이 스크린리더에서 과도하게 중복되지 않는다.
- [ ] `prefers-reduced-motion: reduce`에서 불필요한 움직임이 사라진다.
- [ ] 원본의 캐릭터·이미지를 무단 복사하지 않고 자체 CSS 캐릭터를 사용했다.

최신 Chrome/Edge에서 핵심 기능을 확인한다. macOS/iOS 환경이 있으면 Safari에서도 실제 폼 제출과 모바일 레이아웃을 확인한다. 없는 환경은 검사 완료로 쓰지 않는다. Playwright WebKit 결과를 실제 iOS 기기 검사로 표시하지 않는다.

## 5. 실제 DB·보안 검사

1. 개발 DB에 05 문서의 SQL을 적용한다.
2. 위 평가 문장 중 성공 요청의 requestId와 DB 행을 대조한다. 같은 요청은 1행이어야 한다.
3. 테이블에 원문·이유·IP 컬럼이 없고 앱 로그에 이 값이 출력되지 않는지 확인한다.
4. 개발용 publishable/anon 키로 직접 조회·insert를 시도한다. 접근이 차단되어야 한다. 브라우저에 secret key를 넣어서 검사하지 않는다.
5. 개발 환경에서 형식은 유효하지만 폐기된 테스트 secret key 또는 연결되지 않는 유효한 HTTPS DB 주소를 사용해 분석 성공/저장 실패를 확인한 뒤 복구한다. 빈 키·잘못된 URL 문법은 사전 설정 오류 503이므로 이 장애 검사와 구분한다. 키 값은 보고서에 쓰지 않는다.
6. 30일 초과 테스트 기록 정리를 개발 DB에서 검증한다. 운영 DB를 테스트 목적으로 초기화하지 않는다.

## 6. Vercel 배포 순서

배포를 수행하는 구현 작업에서 아래 절차를 적용한다. 문서 작성 요청만 받았다면 실제 계정·프로젝트를 만들지 않는다.

1. Git에 코드·8개 지침·lockfile·마이그레이션을 포함한다. `.env.local`·비밀값·실제 분석 원문은 제외한다.
2. Vercel에 저장소를 연결한다. Root Directory는 `package.json`이 있는 프로젝트 루트다.
3. Framework Preset Other, Node 24.x, Output Directory public, Build Command 비움을 확인한다. 01 문서의 `vercel.json`과 일치해야 한다.
4. Preview 환경변수 4개를 개발용 키로 등록한다. Production은 운영용 키로 별도 등록한다. 실제 키를 프런트 빌드 변수로 복사하지 않는다.
5. 개발 DB 검증이 끝난 마이그레이션을 운영 DB에 적용한다. 기존 테이블이면 재실행으로 오류를 덮지 말고 현재 스키마와 이력을 확인한다.
6. Preview로 배포하고 아래 스모크 테스트를 수행한다.
7. 공개 Production 전환 전에 WAF 규칙과 사용량 알림을 설정한다. 유료 플랜 변경을 임의 진행하지 않는다.
8. 사용자에게 승인된 배포 범위에서 Production으로 배포한다. 최신 설정을 적용하려면 환경변수 변경 후 재배포한다.
9. Production에서 스모크 테스트를 다시 수행하고 배포 URL·커밋·시각을 기록한다.

환경변수 값이 아니라 **등록 여부와 대상 환경**만 인수인계에 적는다. Preview와 Production 계정 접근이 없으면 코드·배포 설정을 준비하고 외부 작업만 미완료로 남긴다.

## 7. 공개 API 호출 제한

Vercel Firewall의 Rate Limiting을 사용한다. 기준일 확인한 공식 문서는 Fixed Window를 모든 플랜에서 지원하며, Hobby의 rate limit 규칙 수에 제한이 있음을 명시한다. 실제 설정 시 현재 계정의 지원 범위를 재확인한다. [Vercel Rate Limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting)

설정값:

| 설정 | 값 |
| --- | --- |
| 대상 | Request Path **Starts With** `/api/analyze` AND Method Equals `POST` |
| 알고리즘 | Fixed Window |
| 시간 창 | 60초 |
| 허용 횟수 | 10회 |
| 집계 키 | IP |
| 초과 동작 | HTTP 429 |

경로 Starts With를 사용해 `/api/analyze/` 형태도 포함한다. `/api/` 전체를 막는 넓은 규칙을 만들 필요는 없다. 규칙 작성 후 Save → Review Changes → Publish까지 적용 여부를 확인한다. [규칙 설정 문서](https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration)

이 제한은 **IP별·리전별 고정 시간 창** 기준이다. 모든 리전을 합친 전역 제한이나 이동하는 60초 창을 의미하지 않는다. 창 경계와 분산 접근을 완벽하게 막는다고 약속하지 않는다.

검증 시 같은 IP·리전에서 `{ "text": "" }`처럼 AI가 실행되지 않는 잘못된 입력으로 짧게 반복 요청한다. 429와 Firewall 차단 기록을 확인하고 UI의 429 표시도 검사한다. 창 경계 때문에 항상 정확히 11번째가 차단된다고 테스트를 고정하지 않는다. 규칙을 설정할 수 없다면 공개 운영 완료로 표시하지 않고 보호된 Preview에서 검증을 마친다.

OpenAI/Vercel의 사용량 알림을 운영자가 설정한다. 알림은 자동 과금 차단 보장이 아니며 플랜의 실제 제한을 별도로 확인한다. 정확한 금액을 이 문서에서 임의로 정하지 않는다.

## 8. 배포 후 스모크 테스트

스모크 테스트는 배포 직후 핵심 기능이 살아 있는지 빠르게 확인하는 검사다.

| 검사 | 통과 기준 |
| --- | --- |
| `/` 로드·새로고침 | HTML/CSS/JS 200, 콘솔 오류 없음 |
| 직접 `GET /api/analyze` | 405 JSON, HTML 페이지로 바뀌지 않음 |
| 긍정·부정·중립 실제 요청 1회씩 | 라벨·신뢰도·이유 표시, DB 저장 확인 |
| 빈 입력·초과 입력 | 화면 검증, 실제 AI 요청 발생하지 않음 |
| `/api/analyze` 오류 응답 | 고정 메시지, 입력 보존, 재시도 정상 |
| 모바일 화면 | 360px에서 가로 스크롤 없음, 버튼 접근 가능 |
| 비밀 파일 접근 | `/.env.local`, `/AGENTS.md`, `/src/server/openai-client.js`에서 파일 내용 미노출 |
| 브라우저 네트워크 | OpenAI·Supabase로 직접 요청 없음, 응답에 키 없음 |
| 공개 호출 제한 | WAF 429와 사용자 안내 확인 |

정적 파일의 정상 노출(`/js/app.js`, `/css/styles.css`)과 서버 파일 비공개를 혼동하지 않는다.

## 9. 장애 복구와 인수인계

- 새 배포가 주요 기능을 깨뜨리면 Vercel에서 직전 정상 배포로 되돌리고 동일 스모크 테스트를 수행한다. 테이블 삭제로 해결하지 않는다.
- API 키 노출이 확인되면 해당 키를 폐기·재발급하고 환경변수를 갱신해 재배포한다. 노출된 값을 보고서에 재인용하지 않는다.
- 반복되는 AI 오류는 requestId·오류 코드·시각으로 확인한다. 사용자 원문 수집을 임의로 켜지 않는다.
- 결과 캡처·테스트 보고서는 구현 프로젝트의 `artifacts/`에 둔다. 실제 사용자 개인정보가 없는 고정 fixture만 캡처한다.

인수인계 보고서에 아래 항목을 남긴다. 추가 구현 보고서는 프로젝트 산출물이며, 제공된 **지침 6개를 새 지침 파일로 늘리라는 요구가 아니다**.

```text
실행 날짜 / 커밋 / Node·SDK·CLI 버전:
단위·API 검사: 실행 건수, 통과/실패
브라우저 검사: 환경, 화면 크기, 결과
실제 AI 평가: 모델 ID, 12개 라벨 결과, 이유 검토, 추가 문맥 4개
Supabase 검증: 마이그레이션, 저장, 권한, 장애 처리
배포: Preview URL, Production URL, WAF 적용 여부
미실행 항목: 이유와 필요한 접근/설정
남은 문제: 재현 방법과 영향
```

## 10. 최종 완료 판정

- **코드 완료:** 필수 자동 검사 통과, 화면 검수 완료, 문서와 계약 일치.
- **외부 연동 완료:** 실제 지정 OpenAI 모델, Supabase 저장·권한, 품질 기준 검증 완료.
- **배포 완료:** Vercel Production 스모크 테스트와 WAF 검증 완료.

세 단계 모두 통과해야 [PRD의 MVP 완료](../PRD.md)다. 키가 없거나 배포 권한이 없어 실행하지 못한 검사는 `미실행`으로 표시한다. 이 문서에 적힌 테스트 사례는 앞으로 수행할 기준이며 이미 실행한 결과가 아니다.
