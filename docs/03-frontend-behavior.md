# 03. 프런트엔드 기능 구현 지침

> 목적: 버튼을 누르거나 응답을 받았을 때 화면이 어떻게 바뀌는지 정한다. 프런트엔드는 브라우저에서 실행되는 HTML·CSS·JavaScript다. 화면 모양은 [UI 지침](02-ui-design.md), API 필드·오류 코드는 [API·AI 계약](04-api-ai-contract.md)을 따른다.

## 1. 구현 범위와 파일 책임

- 브라우저는 입력 검증, 같은 서비스의 `/api/analyze` 호출, 결과 표시만 담당한다.
- OpenAI·Supabase SDK, 비밀키, 서버 환경변수를 브라우저에 넣지 않는다.
- HTML/CSS/순수 JavaScript를 사용한다. React·Vue·Next.js·TypeScript·UI 프레임워크는 추가하지 않는다.
- 파일은 [프로젝트 생성 지침](01-project-setup.md)의 구조를 따른다. 화면 상태와 이벤트는 `public/js/app.js`에서 관리한다.
- 브라우저 저장소, 쿠키, 분석 이력 기능은 사용하지 않는다. 새로고침하면 입력·결과가 초기화된다.
- 시연용 고정 결과를 실제 API 성공 결과처럼 표시하지 않는다. 테스트용 응답은 테스트 실행 안에서만 주입한다.

## 2. 화면 상태를 한 곳에서 관리하기

상태는 현재 화면이 무엇을 해야 하는지 나타내는 이름이다. 여러 버튼이 제각각 화면을 바꾸지 않도록 `render(state)` 같은 한 함수에서 표시·숨김·비활성화를 처리한다.

| 상태 | 진입 조건 | 종료 조건 |
|---|---|---|
| `idle` | 최초 로드 또는 지우기 | 입력·예시 선택·제출 |
| `editing` | 사용자가 입력을 바꾸거나 예시 선택 | 제출 또는 지우기 |
| `loading` | 클라이언트 검증을 통과한 제출 | 성공·실패·25초 시간 초과 |
| `success` | 성공 응답의 구조와 값 검증 완료 | 입력 변경·다음 제출·지우기 |
| `error` | 입력 검증 실패, 통신 실패, 오류 응답 | 입력 변경·재시도·다음 제출·지우기 |

최소 상태 정보는 `status`, `result`, `error`, `storageStatus`, `activeRequestId`다. 입력 원문은 textarea의 현재 값을 기준으로 읽는다. `activeRequestId`는 브라우저 내부 요청 순번이며 서버가 응답에 주는 `requestId`와 별개다.

다음 원칙을 반드시 지킨다.

1. 입력이 한 글자라도 바뀌면 기존 성공 결과·신뢰도·이유·오류·저장 안내를 모두 지운다. 이전 문장의 결과가 새 문장의 결과처럼 보이면 안 된다.
2. 새로운 제출을 시작할 때도 이전 결과를 지우고 로딩으로 바꾼다.
3. 로딩 중 textarea는 `readOnly = true`, 제출·예시·지우기·재시도 버튼은 `disabled = true`다. 값을 읽거나 복사할 수는 있어야 한다.
4. `status === "loading"`일 때 들어온 모든 제출 이벤트는 무시한다. 화면의 disabled 속성만 믿지 말고 JavaScript에서도 확인한다.
5. 실패를 `neutral`로 변환하거나 신뢰도 `0%`를 표시하지 않는다. 오류와 감성 결과는 서로 다른 상태다.
6. `meta.storage === "failed"`는 `success` 상태를 유지하고 작은 안내만 추가한다.

## 3. 입력 검증

### 글자 수 계산의 단일 규칙

```js
const normalizedText = textarea.value.trim();
const characterCount = Array.from(normalizedText).length;
```

허용 범위는 **앞뒤 공백을 제거한 뒤 1~2,000 Unicode 코드 포인트**다. 코드 포인트는 JavaScript가 문자를 세는 한 방식이다. 일반 한글 한 글자는 1개이며, 이모지 조합은 화면에서 하나처럼 보여도 여러 개로 계산될 수 있다. 화면·서버·테스트가 같은 규칙을 사용해야 한다.

- 입력 도중 원문을 자동으로 `trim()`하거나 잘라내지 않는다. 검증·글자 수·전송 때만 정리된 문자열을 사용한다.
- 중간의 공백, 줄바꿈, 구두점을 바꾸지 않는다. HTML 태그처럼 보이는 문자열도 단순 텍스트다.
- `String.length`는 글자 수 기준으로 쓰지 않는다. HTML `maxlength`도 이 기준과 다르므로 단독 제한 수단으로 쓰지 않는다.
- 2,000자를 넘긴 붙여넣기를 허용하되 글자 수를 오류색으로 표시한다. 전송은 차단하고 수정할 수 있게 한다.
- 빈 입력에서도 제출 버튼은 활성 상태다. 클릭하면 입력 오류를 보여준다. 로딩 외에는 검증 문제 때문에 버튼을 숨기지 않는다.
- 한글 조합 중에는 글자 수 갱신은 가능하지만 제출하지 않는다. `event.isComposing` 또는 `compositionstart`/`compositionend` 플래그로 보호한다.

### 제출 전 검사 순서

1. 로딩 중이면 즉시 종료한다.
2. 조합 중이면 즉시 종료한다.
3. 입력을 `trim()`하고 코드 포인트 수를 계산한다.
4. 0자면 빈 입력 메시지를 표시하고 textarea에 포커스를 준다. 네트워크 요청은 0회다.
5. 2,001자 이상이면 길이 초과 메시지를 표시하고 textarea에 포커스를 준다. 네트워크 요청은 0회다.
6. 통과하면 정확히 한 번 API를 호출한다.

입력 오류 메시지는 [API·AI 계약](04-api-ai-contract.md)의 동일 의미 메시지와 맞춘다. 프런트엔드 검증을 통과했더라도 서버가 반드시 다시 검증한다.

## 4. 버튼·키보드 동작

| 조작 | 동작 |
|---|---|
| 감성 분석하기 | form의 `submit` 핸들러 한 곳에서 검증·요청 실행 |
| Enter | 입력창에 줄바꿈 삽입 |
| Ctrl+Enter / Cmd+Enter | 조합 중이 아닐 때 form 제출; 기본 동작은 막음 |
| 지우기 | 입력을 빈 문자열로, 상태를 `idle`로, 오류·결과를 비운 뒤 textarea로 포커스 이동 |
| 예시 버튼 | 해당 문장으로 입력 전체 교체, `editing` 전환, textarea 포커스; API 호출 없음 |
| 다시 시도 | 현재 textarea 값을 동일한 submit 함수로 전달; 자동 반복 없음 |

예시 문장은 아래 셋으로 고정한다. 버튼 이름을 누르는 것만으로 감성을 결정하거나 결과를 미리 표시하지 않는다.

| 버튼 | 입력할 문장 |
|---|---|
| 기쁜 문장 | 오늘 친구와 오랜만에 만나서 정말 즐거웠어요. |
| 아쉬운 문장 | 기대했던 약속이 취소되어 많이 속상해요. |
| 담담한 문장 | 회의는 내일 오후 세 시에 시작합니다. |

분석 중 버튼을 연속 클릭하거나 키보드 단축키를 반복해도 요청은 한 번만 발생해야 한다. 실패 후 재시도는 새로운 요청이며 별도 API 비용이 발생할 수 있으므로 자동 재시도하지 않는다.

## 5. API 요청

```http
POST /api/analyze
Content-Type: application/json
Accept: application/json

{"text":"오늘 친구와 오랜만에 만나서 정말 즐거웠어요."}
```

- 같은 도메인의 상대 경로 `/api/analyze`로 `fetch()`한다. 브라우저에서 OpenAI·Supabase 주소로 직접 요청하지 않는다.
- 전송 데이터는 `text` 하나다. 모델명, 신뢰도, 감성명, DB 저장 여부를 클라이언트가 지정하지 않는다.
- 요청 본문·API 키·응답의 분석 이유를 콘솔 로그에 출력하지 않는다.
- 요청 시작과 동시에 `AbortController`와 25,000ms 타이머를 만든다.
- HTTP 응답 헤더 수신뿐 아니라 응답 본문 읽기·JSON 해석까지 같은 요청 수명으로 관리한다.
- 서버 AI 요청 제한은 20초, DB 저장 제한은 2초, Vercel 함수 최대 실행 설정은 30초다. 각 제한의 역할은 [API·AI 계약](04-api-ai-contract.md)에 따른다.
- 브라우저 중단이 이미 시작된 서버 처리나 AI 과금을 취소한다는 보장은 없다. 중단 후 자동으로 재요청하지 않는다.

### 권장 제어 흐름

```text
제출 → 입력 검사 → 내부 요청 순번 증가 → loading
  → 25초 타이머 등록
  → fetch + 응답 읽기
  → 현재 요청인지 확인
  → HTTP 상태와 JSON 계약 확인
  → success 또는 error
  → finally에서 타이머 제거·현재 요청의 잠금 해제
```

시간 초과 콜백은 다음 순서로 처리한다.

1. 자기 요청 순번이 현재 `activeRequestId`와 같은지 확인한다. 다르면 화면을 변경하지 않는다.
2. `CLIENT_TIMEOUT` 오류와 `status = "error"`를 설정해 즉시 렌더링한다. 이 단계에서 입력·버튼 잠금을 해제한다.
3. `activeRequestId`를 무효화하고 해당 요청의 AbortController를 중단한다.
4. 뒤따르는 `catch`와 늦은 응답은 요청 순번 불일치로 화면 변경을 건너뛴다. `finally`는 자기 타이머를 항상 정리하지만, 현재 요청의 잠금만 변경할 수 있다.

순번을 먼저 무효화하고 `finally`만으로 잠금 해제를 기다리면 로딩이 계속 남을 수 있으므로 그렇게 구현하지 않는다. 네트워크 실패·정상 완료도 현재 요청인지 확인한 뒤 상태를 정리한다. 종료된 요청이 새 요청의 결과나 로딩을 덮어쓰면 안 된다.

## 6. 응답 검증과 결과 표시

계약의 단일 기준은 [API·AI 계약](04-api-ai-contract.md)이다. 성공 구조는 다음과 같다.

```json
{
  "ok": true,
  "requestId": "49a88e0b-0e14-46da-8c5d-05ec5ed33489",
  "data": {
    "sentiment": "positive",
    "confidence": 87,
    "reason": "즐거웠다는 표현에서 만남에 대한 긍정적인 감정이 드러나요."
  },
  "meta": { "storage": "saved" }
}
```

프런트엔드는 최소한 아래를 검증한 다음 표시한다.

- HTTP 200이고 `ok === true`인가?
- `requestId`가 계약의 UUID 문자열인가?
- `data.sentiment`가 `positive`, `negative`, `neutral` 중 하나인가?
- `data.confidence`가 유한한 정수이며 0 이상 100 이하인가?
- `data.reason`이 문자열이며 앞뒤 공백을 제거한 뒤 1~200 코드 포인트인가?
- `meta.storage`가 `saved` 또는 `failed`인가?

하나라도 실패하면 결과를 보정하거나 임의 값을 채우지 않는다. 잘못된 응답 안내를 표시한다. 이유의 한국어·문장 수 품질은 서버 프롬프트와 수동 검증 기준으로 관리하며, 프런트엔드에서 한국어 비율이나 문장부호 개수로 재판정하지 않는다.

| API 값 | 사용자 표시 |
|---|---|
| `positive` | 긍정 |
| `negative` | 부정 |
| `neutral` | 중립 |
| `confidence: 87` | 신뢰도 87%; 막대 너비 `87%` |
| `reason` | 분석 이유 아래 일반 텍스트 |
| `storage: "failed"` | “분석은 완료했지만 운영 기록을 저장하지 못했어요.” |

`confidence`는 0~100 정수이므로 100을 다시 곱하지 않는다. 숫자를 임의로 반올림·보정하지 않는다. `0`도 유효한 값이므로 `if (confidence)`로 존재 여부를 판단하지 않는다.

사용자 입력, 분석 이유, 서버의 안전한 안내 문구는 `textContent`로 넣는다. `innerHTML`, `insertAdjacentHTML`, Markdown 렌더러로 출력하지 않는다. 감성명으로 CSS 클래스를 만들 때도 고정된 세 가지 매핑만 허용한다.

## 7. 오류·비JSON 응답 처리

정상적인 오류 응답은 다음 형태다. 실제 코드·문구·HTTP 상태는 [API·AI 계약](04-api-ai-contract.md)의 표를 사용한다.

```json
{
  "ok": false,
  "requestId": "49a88e0b-0e14-46da-8c5d-05ec5ed33489",
  "error": {
    "code": "AI_TIMEOUT",
    "message": "분석 시간이 길어지고 있어요. 잠시 후 다시 시도해 주세요.",
    "retryable": true
  }
}
```

- 알고 있는 오류 코드만 화면의 고정 메시지와 연결한다. 공급자 응답 원문, stack trace, HTML 오류 페이지를 보여주지 않는다.
- 알 수 없는 코드·잘못된 구조·JSON 해석 실패는 일반적인 응답 오류로 처리한다.
- Vercel·방화벽이 반환한 429·503·504·413 응답은 JSON이 아닐 수 있다. 본문이 HTML이어도 HTTP 상태에 맞는 안전한 고정 안내를 표시한다.
- 429는 잠시 후 재시도 안내, 503은 일시적 서비스 장애 안내, 504는 처리 지연 안내로 연결한다. `Retry-After`를 UI에 반영한다면 숫자인 초 값만 사용하고, 해석할 수 없는 값은 무시한다.
- JSON이 아닌 기타 HTTP 오류는 일반 오류 안내를 표시한다. `response.ok`만 보고 성공으로 판정하지 않는다.
- 유효한 앱 오류 JSON이면 그 안의 알려진 code와 검증된 retryable을 먼저 적용한다. 상태 코드 기반 대체는 앱 오류 JSON이 없거나 유효하지 않을 때만 사용한다. 따라서 HTTP 503 CONFIGURATION_ERROR의 retryable false를 일반 503의 true로 덮어쓰지 않는다. HTTP 413은 내용 수정 안내이며 재시도 버튼을 표시하지 않는다.
- 네트워크 실패는 연결 확인 안내, 브라우저 25초 중단은 처리 지연 안내로 구분한다.
- `retryable === true`인 오류에만 결과 영역의 “다시 시도” 버튼을 표시한다. 플랫폼 429·503·504와 네트워크·브라우저 시간 초과도 재시도 안내를 제공한다.
- 입력 문제·응답 거절은 내용을 고치도록 안내한다. 기본 분석 버튼은 로딩 종료 후 다시 활성화한다.
- 오류가 발생해도 입력 문장은 보존한다. 결과값은 비우며 중립 결과로 대체하지 않는다.

서버가 보내는 `requestId`는 디버깅용 식별자다. 사용자의 입력을 담지 않으며 기본 UI에 긴 UUID를 노출하지 않는다.

| 이모지·한글·앞뒤 공백 | 프런트엔드와 서버의 글자 수 일치 |
| 예시 3개 | 정확한 문장 입력, 자동 분석 0회 |
| 연속 클릭·단축키 반복 | 로딩 중 요청은 1회 |
| 한글 조합 중 단축키 | 전송하지 않음 |
| 분석 중 | textarea 읽기 전용, 모든 동작 버튼 비활성 |
| 성공 3종 | 감성명·0~100 신뢰도·이유가 계약대로 표시됨 |
| 신뢰도 0·100 | 숫자 및 막대가 정확히 표시됨 |
| 입력 수정·지우기 | 이전 결과·오류·저장 안내가 사라짐 |
| 잘못된 감성명·범위 초과·누락 필드 | 임의 보정 없이 응답 오류 표시 |
| 오류·거절·시간 초과 | 입력 보존, 결과 없음, 로딩 해제 |
| HTML로 반환된 429·503·504 | JSON 파싱 실패로 화면이 멈추지 않고 고정 오류 안내 |
| 저장 실패 | 성공 결과 유지, 저장 안내만 표시, 자동 재호출 0회 |
| 늦은 응답 | 종료된 요청이 새 화면을 덮어쓰지 않음 |
| HTML·스크립트처럼 보이는 이유 | 문자 그대로 표시되고 코드 실행 0회 |
| 새로고침 | 입력·결과·오류 초기화, 저장소에 내용 없음 |

통신 상태와 예외를 재현하는 테스트 방법은 [테스트·배포 지침](06-testing-deployment.md)을 따른다. 프런트엔드 완료는 예쁜 성공 화면 하나로 판정하지 않고 위 상태 전환 전체로 판정한다.
